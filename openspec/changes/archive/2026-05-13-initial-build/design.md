## Context

SMDR2 is a web tool for semiconductor back-end packaging engineers. The
input is DXF files (typically ~100k entities); the eventual output is a
QA report generated by an existing design rule checker that consumes a
specific Match JSON shape. Between input and output sits the interactive
classification work — engineers visually verify which entities are which
class of object (SMD, BGA ball, substrate, etc.) using a growing template
library.

The system already had a Gemini-built v0 that suffered from SVG render
offsets in selection hit-testing. This design starts from scratch with a
Canvas-2D pipeline.

## Goals / Non-Goals

**Goals:**
- Render large DXFs (~100k entities) interactively in a browser without
  visual offsets between cursor and hit-test.
- Let one operator process multiple DXFs in parallel: background
  parsing + pre-match so opening a file is instant.
- Multi-library template store so different customers can have
  independent template sets without leaking templates across jobs.
- Single matching engine that handles single-entity templates (a BGA
  ball) and multi-entity templates (a 3-line fiducial mark) under
  rotation / mirror / scale / tolerance.
- Output a Match JSON that the existing design rule checker can consume
  unchanged.
- AutoCAD-style mouse and keyboard interactions so domain users feel at
  home.

**Non-Goals:**
- A real DRC implementation (mocked here; real one is owned elsewhere).
- Multi-user / multi-tenant deployment (single operator MVP).
- WebGL renderer (Canvas 2D is fast enough at the target scale).
- Editing the DXF itself.

## Decisions

### Server-side DXF flatten, client-side Canvas render

ezdxf is the most complete DXF library in any ecosystem and correctly
handles OCS arbitrary-axis transforms, INSERT expansion, bulge → arc,
MTEXT positioning, and DIMENSION block synthesis. None of the
JavaScript DXF libraries we evaluated handled all of these. Doing the
parse server-side and shipping primitives (line / polyline /
filled_polygon / point) lets us reuse the same flattening for matching
and for render.

Alternative considered: client-side parsing with `dxf-viewer`. Rejected
because rendering offsets in the Gemini build came from the JS parser's
incomplete OCS handling. Switching parsers would have shifted the bug
elsewhere, not fixed it.

### Canvas 2D over SVG or WebGL

SVG with 100k DOM nodes is unworkable on Chromium. WebGL requires a
shader pipeline that doesn't pay for itself at this scale. Canvas 2D
with viewport culling and dirty-rect repaint hits 60 fps comfortably for
24k primitives in the sample DXF, and we can scale to 100k with the
same approach.

A direct consequence: hit-testing happens in screen→world coords that
share the exact transform used for render, so the previous offset class
of bugs can't recur. The `ResizeObserver` on the canvas catches layout
shifts (e.g., class toolbar populating after fetch) that would otherwise
leave the canvas internal buffer at the wrong resolution.

### Multi-library SQLite store

One SQLite file (`data/library.sqlite`) backs everything: `libraries`,
`classes` keyed by `(library_id, name)`, `templates` keyed by `id`, and
the `files` table. WAL mode lets subprocesses (the ProcessPool workers)
read the latest committed templates without blocking the main process's
writes.

Alternative considered: a separate SQLite file per library. Rejected as
overkill — cross-library queries (e.g., listing libraries with their
counts) become awkward, and the on-disk layout becomes harder to back up
or share. The single-file design also makes migrations easier.

Schema migrations are detected and run on Store init. The pre-multi
schema (no `library_id` column anywhere) is supported: `classes` is
rebuilt with the new composite PK, `templates` is rebuilt to drop the
stale `class_name → classes(name)` FK, and `files.library_id` is added
via `ALTER TABLE`.

### Pose-based multi-entity matching

For single-entity templates the naive scan over candidates is fine. For
multi-entity templates (e.g., a 3-piece SMD pad), the first attempt
"gather every entity in a bounding-box radius around a seed and bulk
chamfer" failed: closely-packed neighbouring SMDs swept extra entities
into the candidate cloud, blowing the point-count gate and rejecting
real matches.

The fix is pose-based: pick the rarest template entity as the seed,
encode every other template entity's centroid in the seed's PCA-local
frame, then for each candidate seed in the drawing predict where each
other template entity should be and look for matching shapes at exactly
those positions. Result on the sample DXF: SMD template (3 entities,
non-square rectangles) finds all 63 other SMDs (matching ground truth)
with zero spurious matches, in 65 ms.

### N_JOBS as an env var, default 1

After single-process optimisations (cached template state, brute-force
chamfer below 50 points, early-exit on the first sub-tolerance variant),
the 24k-entity BGA single-entity match dropped from 6.1 s to 1.0 s.
That's fast enough for interactive use, so multiprocessing isn't on by
default — its spawn overhead dominates for small workloads.

`SMDR2_N_JOBS=N` (or the `n_jobs` keyword to `find_matches`) opts in to
a lazy module-level `ProcessPoolExecutor`. The pool persists across
calls so the spawn cost is paid once. n_jobs=4 takes the same workload
to 0.5 s.

### Drop the closing duplicate of closed polylines

Flattened closed polylines have N+1 points (last == first). Including
the duplicate in centroid + PCA biases both: PCA gives axes tilted by a
small angle, and the four sign-flip variants in the alignment search no
longer cover the mirror case. We drop the duplicate before computing
the centroid and PCA, but compute `path_length` on the full sequence so
closed shapes still report their perimeter.

This was caught by a unit test for mirror alignment of a rectangle and
applies to every closed shape in real DXFs.

### Cache layer: in-memory LRU over parsed JSON

Parsed primitives + shape index are cached with `functools.lru_cache`
keyed by `(path, mtime_ns)`, size 4. This is enough for the operator's
"flick between a few files" workflow without unbounded memory growth.

### Per-class colour palette as a single shared source of truth

`CLASS_COLORS` in `app/static/canvas.js` is the only place class colours
are defined. Class toolbar buttons set `--class-color` as a CSS custom
property; scan-all overlay reads the same map; library modal thumbnails
draw in the class colour. Adding a new class only requires extending
this map (and the backend's `DEFAULT_CLASSES` if it should be seeded).

### Mock DRC behind a stable function signature

`check_rules(dxf_path, match_json, entity_shapes=None) → RuleChecking
JSON` is the contract with the downstream design rule checker. The
current implementation is a mock that ships one geometric rule
(substrate-to-first-SMD distance > 5 mm). Replacing it with the real
checker should be a drop-in module swap; the entity_shapes kwarg gives
the real checker the geometry it needs without re-parsing the DXF.

## Risks / Trade-offs

- **In-process state for jobs and matching pool**. Job dict and worker
  pool live in the FastAPI process; uvicorn auto-reload kills them.
  Files retain their persistent metadata so reload "loses" only the
  job list, but in-flight pre-process jobs are interrupted. Mitigation:
  on startup, any file not at `ready_to_match` whose parsed/prematch
  cache is missing gets a fresh preprocess job submitted.

- **Library cache in subprocess can lag the parent**. Each
  ProcessPoolExecutor worker has its own `LibraryRegistry` and SQLite
  connection. We work around this by reading templates fresh from
  SQLite at the start of every pre-match (subprocess) — WAL gives us
  read-after-write consistency from the main process's writes.

- **SQLite migration is not reversible**. If a schema change is wrong
  there is no rollback path baked in. Mitigation: keep migrations
  additive where possible, and the test suite hits a tmp-path DB so
  changes can be validated before touching the real file.

- **Match JSON references handles, which are per-file**. Reassigning a
  file to a different library invalidates any saved Match JSON for
  that file (the templates change so the matches change). We trigger
  a re-preprocess on library switch so the prematch overlay is fresh,
  but the persisted Match JSON is left stale until the user re-runs
  Save Match. Acceptable for MVP; document the contract.

- **Single test DXF**. Tests that require ground truth use the bundled
  `data/test.dxf`. If that file is missing the test skips. For broader
  coverage we should add synthetic small DXFs to the test fixtures.
